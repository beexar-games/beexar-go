# Wallet conformance fixtures

One fixture set, run by all four Beexar SDKs (`sdk/{node,go,php,python}`)
against the in-memory reference wallet each of them ships in its `examples/`.
Behaviour cannot diverge between languages while there is only one set of
cases.

Generated by `sdk/tools/gen-fixtures.mjs` (`make sdk-fixtures`) and committed.
CI (`test:sdk:node`) regenerates and fails on a diff, an untracked case
directory included — the signature is derived from the body, so a fixture whose
signature does not match its own bytes cannot exist.

## Layout

```
manifest.json          fixture_version + the case list
secret.txt             the shared HMAC secret, exact bytes, NO trailing newline
cases/<nnnn-name>/
  request.json         { endpoint, kind, headers }   headers is {} when the case omits the signature
  request.body         the exact request bytes
  ledger.before.json   wallet state the handler starts from
  response.json        { status, body }
  ledger.after.json    wallet state it must end in
```

## Two comparison modes, deliberately different

- **`request.body` is compared byte for byte.** That is the entire point: the
  signature is an HMAC over bytes, so an SDK that parses and re-serialises
  before verifying must fail. Several bodies use a key order no serialiser
  emits (`0004-key-order-hostile`) precisely to catch that.
- **`response.json.body` is compared JSON-equal.** Key order and whitespace
  legitimately differ between languages and carry no meaning here.

## The stored signature is re-derived

Every runner recomputes `X-REQUEST-SIGN` from `request.body` and `secret.txt`
and fails when the stored value differs: a fixture whose signature drifted from
its bytes would otherwise test nothing. Only a **well-formed** header is
re-derived — 64 lowercase hex characters (`^[0-9a-f]{64}$`) other than the
all-zeros `wrong` sentinel. Anything else *is* the case (fixture version 3):
`0033-signature-non-ascii` carries 64 Latin-1 letters on purpose — the right
length, not hex. A character count lets it through, and in a language where
those characters encode to more than 64 bytes a constant-time compare over the
bytes throws instead of answering false. The expected answer is the ordinary
signature refusal, HTTP 400 with api_code `403`; a 500 means the SDK crashed.

## `kind`

- `transport` — the request never reaches the handler (bad, missing or
  malformed signature, oversize body, invalid amount, invalid currency). The
  ledger is unchanged.
- `ledger` — the handler runs. `ledger.before.json` → `ledger.after.json` is
  part of the assertion, which is what makes these fixtures test semantics
  (idempotency, tombstones, batch atomicity) and not just transport.

## Amount scale on `/freespins/finish`

The wallet spec keeps SoftSwiss's pattern for `amount` — up to 18 fractional
digits (`^\d{1,18}(\.\d{1,18})?$`). The four SDKs parse it with the same shape
check as every other amount, which stops at 16 fractional digits: that is the
platform's own money scale, and a freespins issue is only ever denominated in a
currency of at most 12 decimals, so Beexar never sends more than the currency's
scale. The gap is therefore unreachable from the platform;
`0032-freespins-finish-amount-scale-overflow` (17 fractional digits) pins the
refusal — HTTP 400, api_code `400`, `amount: not a valid decimal amount` — so
no SDK quietly widens it on its own.

## Ledger shape

```json
{
  "accounts":     { "<account_id>": { "currency": "EUR", "balance": "100.00", "bet_limited": false } },
  "transactions": { "<id_provider>": { "id": "<operator tx id>", "balance_after": "90.00",
                                       "type": "bet|win", "amount": "10.00" } },
  "tombstones":   ["<id_provider>"],
  "freespins_issues": { "<issue_id>": { "account_id": "player_1", "currency": "EUR",
                                        "status": "issued|canceled|finished",
                                        "amount": "12.50", "balance_after": "112.50" } }
}
```

`type` and `amount` are recorded only for transactions a rollback can reverse.

`freespins_issues` (fixture version 2) are the freespins the operator issued,
recorded before Freespins/Issue was sent: `/freespins/finish` carries only
`issue_id` and `amount`, so the issue is what names the player and currency to
credit. `amount` and `balance_after` appear once the result is credited; a
repeated `/freespins/finish` answers that `balance_after` and credits nothing.
An unknown `issue_id` is refused with api_code `610`, a canceled issue with
`605`.
Operator transaction ids are a deterministic `op-tx-<n>` sequence and round ids
`op-round-<n>`, both starting at 1 per case, so the expected responses are
stable.
