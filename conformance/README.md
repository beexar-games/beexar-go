# Wallet conformance fixtures

One fixture set, run by all four Beexar SDKs (`sdk/{node,go,php,python}`) and by
the in-memory reference wallets in `sdk/examples/wallet-inmemory/`. Behaviour
cannot diverge between languages while there is only one set of cases.

Generated by `sdk/tools/gen-fixtures.mjs` (`make sdk-fixtures`) and committed.
CI regenerates and fails on a diff — the signature is derived from the body, so
a fixture whose signature does not match its own bytes cannot exist.

## Layout

```
manifest.json          fixture_version + the case list
secret.txt             the shared HMAC secret, exact bytes, NO trailing newline
cases/<nnnn-name>/
  request.json         { endpoint, kind, headers }   headers is {} when the case omits the signature
  request.body         the exact request bytes
  ledger.before.json   wallet state the handler starts from
  response.json        { status, body }
  ledger.after.json    wallet state it must end in
```

## Two comparison modes, deliberately different

- **`request.body` is compared byte for byte.** That is the entire point: the
  signature is an HMAC over bytes, so an SDK that parses and re-serialises
  before verifying must fail. Several bodies use a key order no serialiser
  emits (`0004-key-order-hostile`) precisely to catch that.
- **`response.json.body` is compared JSON-equal.** Key order and whitespace
  legitimately differ between languages and carry no meaning here.

## `kind`

- `transport` — the request never reaches the handler (bad signature, oversize
  body, invalid amount, invalid currency). The ledger is unchanged.
- `ledger` — the handler runs. `ledger.before.json` → `ledger.after.json` is
  part of the assertion, which is what makes these fixtures test semantics
  (idempotency, tombstones, batch atomicity) and not just transport.

## Ledger shape

```json
{
  "accounts":     { "<account_id>": { "currency": "EUR", "balance": "100.00", "bet_limited": false } },
  "transactions": { "<id_provider>": { "id": "<operator tx id>", "balance_after": "90.00",
                                       "type": "bet|win", "amount": "10.00" } },
  "tombstones":   ["<id_provider>"]
}
```

`type` and `amount` are recorded only for transactions a rollback can reverse.
Operator transaction ids are a deterministic `op-tx-<n>` sequence and round ids
`op-round-<n>`, both starting at 1 per case, so the expected responses are
stable.
